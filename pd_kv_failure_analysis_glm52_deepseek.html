1. 结论摘要

GLM5.2

P 端 Store load 返回失败码或 None：单 KV group 的失败 block 会进入 invalid_block_ids，再由 scheduler 按 P 端的 kv_load_failure_policy=recompute 回退重算。

D 端 Mooncake pull 失败：MooncakeConnectorV1 会记录失败请求和失败 block，同时仍完成 transfer task 与 P 端资源清理；最终 D 端配置 fail，scheduler 应将请求置为错误结束，而不是重算。

存在失败上报通道

DeepSeek Flash

P 端 Store load 失败：hybrid 多 KV group 分支明确“跳过 invalid-block fallback”，只打印错误，不把失败 block 上报 scheduler。

D 端 Mooncake pull 失败：MooncakeHybridConnector 捕获并记录异常，但在 finally 中仍标记接收任务完成、发送 DONE/ACK 清理信号；它没有失败 block 上报接口。

当前可出现既不停也不重算
最关键差异：GLM 的 connector 链路能把失败块送入 scheduler；DeepSeek Flash 当前两个失败点都存在“日志可见、控制面不可见”的缺口。

2. P 节点 Store load 的公共入口

P 节点使用 MultiConnector 时，AscendStoreConnector 负责 prefix lookup 与从 Mooncake Store 恢复 KV；Mooncake P2P connector 负责随后 P→D 的 KV 传输。这是两个独立阶段。

2.1 “prefix 命中”不等于“load 成功”

Lookup根据 hash/key 返回命中 token 数
→
Allocatescheduler 为命中的外部 KV 分配本地 block
→
Store getbatch_get_into_multi_buffers 真正拷入 NPU KV 地址
→
Failure report根据返回码生成 failed block，或因 hybrid 限制仅记日志

2.2 MooncakeBackend 对失败的归一化

  • 底层返回负值：保留负错误码并返回结果列表。
  • 底层抛异常：backend 捕获异常、记录日志并返回 None。
  • 正值会被归一化成 0；当前代码把 0 当成功、非 0 当失败。

依据：mooncake_backend.py:224-270。

2.3 同步与异步 load

模式执行位置完成方式失败记录

3. GLM5.2：MooncakeConnectorV1

结合提供的配置：P 端 AscendStore load_async=False、failure policy 为 recompute；D 端 MooncakeConnectorV1、failure policy 为 fail。

3.1 P 节点 prefix 命中后 Store load 失败

Store get返回非 0 列表或 None
→
定位失败块record_failed_blocks
→
单 group写入 worker 的 _invalid_block_ids
→
Connector output通过 get_block_ids_with_load_errors 上报
→
Scheduler识别受影响请求并回退 computed token
  1. KVPoolWorker._load_direct_sync_chunks() 调用 m_store.get()。
  2. _record_sync_load_failures() 把失败返回码映射成本地 block id。
  3. GLM5.2 是单 KV cache group 时，失败 id 加入 _invalid_block_ids。
  4. AscendStoreConnector.get_block_ids_with_load_errors() 把集合交给 model runner 的 connector output。
  5. scheduler 的 _handle_invalid_blocks() 找到受影响请求；在 recompute 策略下跳过本轮正常输出并调整请求状态，让失败范围重新计算。
P 端结果：不会把这批失败 KV 当成有效 prefix 直接交付 D；预期是 P 端对失败范围重算。recompute_scheduler_enable=False 不会把 policy 改成 fail——该开关是 PD consumer 的专用 RecomputeScheduler/抢占机制，KV load failure policy 是另一条机制。

边界条件

  • 这里的结论针对 Store get 返回码/None；MooncakeBackend 已将自身捕获到的 get 异常转换为 None。
  • 如果失败 block 没有经过 MultiConnector 汇总进最终 connector output，scheduler 就看不到失败；运行时需检查 invalid_block_ids。
  • 失败在 forward 前已写入目标地址，但 scheduler 是在 model runner output 返回后处理，因此本轮结果必须被跳过，不能接受该轮采样输出。

3.2 D 节点通过 MooncakeConnectorV1 拉取 KV 失败

Mooncake readbatch_transfer_sync_read 返回 < 0 或抛异常
→
捕获失败transfer_failed=True
→
标记request 加入 failed set；local blocks 加入 invalid set
→
清理仍 task done、DONE_RECVING、释放 P 端资源
→
上层策略D 配置 fail → 请求 FINISHED_ERROR
  1. 传输函数在返回码小于 0 时抛 RuntimeError。
  2. _handle_request() 捕获异常，调用 _mark_failed_recv_request()；同一请求后续 shard/task 会被跳过并继续标失败。
  3. 无论成功失败，finally 都减少 task 计数；最后一个 task 会调用 task_tracker.update_done_task_count()。
  4. 无论成功失败，都向 P 端发送完成/清理信号，避免 P 端 block 与端口泄漏。这个 DONE 表示“传输生命周期结束”，不表示“KV 内容有效”。
  5. worker 通过 get_block_ids_with_load_errors() 取走 invalid block；scheduler 根据 D 端 kv_load_failure_policy=fail 将受影响请求错误结束并返回空 token 输出。
容易误判的日志：P 端收到 DONE/ACK 并释放 KV，并不能证明 D 拉取成功。成功与失败都走同一资源清理协议，必须结合 D 端 Failed to transfer KV cache 与 scheduler 的 FINISHED_ERROR 日志判断。

4. DeepSeek Flash：MooncakeHybridConnector

DeepSeek Flash 使用 hybrid/compressed KV cache 多 group。当前 AscendStore 与 MooncakeHybridConnector 都没有形成完整的失败闭环。

4.1 P 节点 prefix 命中后 Store load 失败

Store get返回非 0 或 None
→
定位失败块生成 missing block ids
→
多 group 分支只打印错误
→
不上报不写入 _invalid_block_ids
→
继续同步路径继续 forward；异步路径标记 recv finished
KV load failed for hybrid request %s.
Skip invalid-block fallback to avoid scheduler crash.
failed_blocks=%s

同步路径的 _record_sync_load_failures() 和异步路径的 _record_load_failures() 都有同样的保护：当 len(block_ids_by_group) > 1 时不更新 invalid block 集合。

P 端结果：当前只有错误日志，没有请求级 fail，也没有 recompute。同步 load 会继续进入 forward；异步 load 会把请求加入完成集合。若失败地址仍保留旧值/未初始化内容，后续计算与 P→D 传输存在错误 KV 风险。

此外，平台校验明确禁止 hybrid 模型使用 kv_load_failure_policy=recompute，因此即使启动参数尝试设置 recompute，也会在配置校验阶段 assert，而不是获得回退能力。

4.2 D 节点通过 MooncakeHybridConnector 拉取 KV 失败

Mooncake read返回 < 0 后抛 RuntimeError
→
内部捕获只执行 logger.exception
→
finally仍发送 remote-port cleanup 与 DONE_RECVING
→
标记完成最后 task 更新 task tracker
→
Scheduler 视角只看到 recv finished，看不到 invalid block

MooncakeHybridConnector._handle_request() 在内部吞掉传输异常；与 MooncakeConnectorV1 不同，它没有：

  • failed_recv_requests 请求失败集合；
  • invalid_block_ids 失败块集合；
  • get_block_ids_with_load_errors() 对外接口。
D 端结果：当前代码会把失败的拉取任务当作“生命周期已完成”上报，scheduler 无法依据 fail 或 recompute policy 做动作。因此你描述的“既不会停止，也不会重算”与当前代码一致。

6. 风险、运行时验证点与修复方向

6.1 建议抓取的关键日志/状态

GLM5.2

  • Failed to get ... keys
  • connector output 中的 invalid_block_ids
  • scheduler 是否调用 invalid-block handler
  • D 端 Failed to transfer KV cache
  • 最终请求是否 FINISHED_ERROR

DeepSeek Flash

  • Skip invalid-block fallback to avoid scheduler crash
  • Failed to transfer KV cache
  • 失败后是否仍出现 receive finished / DONE_RECVING / ACK
  • 确认没有 invalid block output
  • 观察后续 decode 是否继续并出现错误输出

6.2 当前最需要补齐的代码能力

  1. Hybrid Store load：需要 group-aware 的 invalid-block 表达与 scheduler 回退，不能简单把多个 group 的 block id 扁平为一个集合。
  2. MooncakeHybridConnector：仿照 MooncakeConnectorV1 增加 request failure tracking、各 group 的失败 block 上报，并在所有 pull task 完成后保留失败状态。
  3. Policy：让上层明确区分 fail 与 group-aware recompute；在 recompute 尚未支持前，至少 fail-fast，避免使用不完整 KV 继续 decode。
  4. 协议语义：资源清理 DONE 与数据成功必须分离；DONE 可继续用于释放 P 资源，但还应有独立 success/failure 状态。
  5. 测试：补充“lookup hit + get miss/错误码”“部分 TP/PP task 失败”“最后 task 失败”“多 group 部分失败”的回归测试。
安全优先建议：在 DeepSeek group-aware recompute 完成前，D pull 或 P Store load 失败应让请求显式 FINISHED_ERROR；继续 decode 的静默错误风险高于失败返回。
