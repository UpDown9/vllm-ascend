Mooncake put 前置 CPU 操作并行化修改方案

目标：将 Mooncake store 写入路径中与数据内容无关的 CPU 元数据工作（chunk 构造、key 序列化、lookup、缺失项过滤，以及可安全提前的地址描述准备）与模型推理重叠，缩短从 block 分配到实际 put 的关键路径。

核心结论：采用严格的两阶段模型：block 分配完成后立即触发 prepare_save，forward 完成后只执行 commit_save。commit 阶段不再做 group/chunk 构造、key 序列化、lookup 或 missing 过滤；只消费已确定的待写入 batch，等待对应 event 后调用 put。

1. 当前路径与瓶颈

普通路径位于 vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py：

block_ids / block_hashes 已在 ReqMeta 中确定
  -> process_transfer_chunks_with_block_ids()
  -> chunk.key.to_string()
  -> lookup(keys)
  -> 过滤 missing keys
  -> prepare_transfer_value()
  -> event.synchronize()
  -> m_store.put()
  • 普通路径的关键代码：_handle_request，约第 395–499 行。
  • layerwise 路径已有 key，仍会执行 key 转换、lookup、地址/大小准备和最终 put，约第 842–905 行。
  • 传输线程已经独立运行（KVCacheTransferThread.run），因此第一阶段可以利用现有线程实现重叠。

3. 建议的接口改造

3.1 引入可复用的预处理结果

新增内部数据结构（建议放在 kv_transfer.py 或相邻 metadata 模块）：

PreparedPut(
    keys: list[str],
    chunks: list[TransferChunkWithBlockId],
    missing_indices: list[int],
    block_ids: list[int],
    kv_cache_group_id: int,
    # 可选：提前生成的 addrs/sizes
  )

预处理结果与 req_id/event_id 绑定，避免后续线程重复构造 key 和重复 lookup。

3.2 将 _handle_request 拆成两个阶段

触发时机：不能在 wait_for_save() 中首次提交完整请求；该函数通常已经位于 forward 之后。应在 connector metadata（block 已分配）可用、模型执行开始前调用 prepare_requests(metadata.requests)，并在 wait_for_save() 中调用 commit_requests()。
阶段职责允许并行的内容
Prepare根据已分配 block 生成 chunks/keys，调用 lookup 并过滤已存在项完全 CPU/metadata；可与模型推理并行
Commit确认源 KV 数据就绪，准备最终地址，调用 Mooncake put只能在 NPU event ready 后提交数据

建议先在现有传输线程内拆分函数，不立即增加更多线程：

prepared = self._prepare_put_metadata(req_meta)
prepared.addrs, prepared.sizes = self._prepare_put_buffers(prepared)
event.synchronize()
self._commit_put(prepared)

3.3 lookup 结果的保守语义

预处理阶段的 lookup 只用于过滤明显已存在的 key。提交阶段仍需允许 Mooncake 返回“已存在/重复写入”等结果，不能假设预处理结果绝对有效。

4. 生命周期与并发约束

  • Block pin：从提交预处理任务开始，到 put 完成并收到完成事件之前，不能释放或复用相关 NPU block。
  • 数据就绪：prepare_transfer_value 若会读取/拷贝 tensor 数据，必须推迟到 event 完成；若仅计算地址和 size，则可提前。
  • 线程安全：预处理结果、完成状态和 block 引用需要按 event_id/req_id 管理，并在异常路径清理。
  • 背压：为预处理队列设置最大长度；队列过长时回退为同步处理，避免 CPU 内存和 metadata RPC 堆积。
  • TP/DCP/layerwise：保持现有 sharding、group、mask 和 chunk granularity 逻辑，不在并行化改造中改变 key 选择规则。

5. 分阶段实施

  1. 阶段一：低风险拆分。仅提取 prepare/commit 函数，复用当前传输线程；增加计时日志和 feature flag，验证行为不变。
  2. 阶段二：提前触发。在 scheduler/connector 生成 ReqMeta 后立即提交 CPU 预处理任务；模型执行和 lookup 并行。
  3. 阶段三：地址描述前置。确认各 token_database.prepare_transfer_value 实现不读取未就绪数据后，再将 addrs/sizes 也前置。
  4. 阶段四：性能调优。调整队列深度、worker 数、批量 lookup 大小和超时策略；必要时增加按请求合并的 metadata 任务。

6. 测试与验收

类别验证项
功能重复 key、全部命中、全部 miss、部分 miss、空 chunk、异常和取消请求。
并发模型推理期间 lookup/prepare 正常运行；block 不提前释放；event 未完成时不会提交 put。
兼容性普通路径、layerwise、TP/DCP、hybrid cache、lazy init。
性能记录 metadata prepare、lookup、event wait、Mooncake put 的耗时及重叠比例；比较端到端吞吐和 P99 延迟。
回归运行相关 tests/ut/distributed、KV transfer 测试，以及 NPU 上的端到端用例。

7. 风险与回滚

主要风险是 block 生命周期错误、lookup 结果过期导致重复写入处理不当，以及某些后端在 prepare_transfer_value 中隐含读取 tensor 数据。建议默认关闭新流水线，通过 feature flag 灰度启用，并保留原有同步路径作为回退。

回滚方式：关闭 feature flag 即恢复现有 lookup -> prepare -> synchronize -> put 顺序；不改变 Mooncake backend API。

8. 推荐验收标准

  • 功能测试结果与原路径一致，尤其是部分命中和重复写入场景。
  • 无未完成 NPU event 下的非法读、写或 block reuse。
  • CPU 预处理时间至少有一部分被模型计算隐藏；端到端延迟不因队列等待显著增加。
  • 异常、超时、进程退出时所有预处理任务和 block 引用均可清理。
