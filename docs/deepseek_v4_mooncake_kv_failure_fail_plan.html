DeepSeekV4 Mooncake 多 KV Group 失败上报与请求 Fail 方案

仓库：/home/xujiuxu/code/vllm-ascend　生成日期：2026-08-29　目标：只处理多 KV group 的 KV load/pull 失败，使用扁平 block ID 识别请求并返回 proxy 错误，不做 recompute。
推荐结论

复用现有的 KVConnectorOutput.invalid_block_ids → RecomputeScheduler → FINISHED_ERROR 链路，不新增 group_id、request-level 字段，也不修改上游输出 dataclass 和聚合器。只需补齐三点：Hybrid Mooncake worker 在所有 KV group 的传输异常时上报扁平本地逻辑 block ID、V1 connector 遍历所有 group，以及Ascend RecomputeScheduler 遍历请求的全部 group 并直接 fail。

一、当前代码事实

环节当前实现问题
DeepSeekV4 KV cacheMLAAttentionSpec、indexer cache、compressor/SWA cache 会形成多个 KV group；当前使用 AscendHybridKVCacheCoordinator。失败 block 必须跨 group 判断，不能再使用单 group 解包。
MooncakeConnectorV1KVCacheRecvingThread._mark_failed_recv_request() 已存在，但只把 local_block_ids[0] 放入 invalid 集合。多 group 失败时可能漏报 group 1 及以后。
MooncakeHybridConnectorKVCacheRecvingThread._handle_request() 捕获传输异常并打印日志，随后完成 task tracker。没有 invalid block 集合，也没有实现 get_block_ids_with_load_errors()，Scheduler 收不到失败。
Worker/Executor已有 KVConnectorOutput.invalid_block_ids: set[int]，多 worker 输出由 vLLM 的聚合链路合并。每个失败 worker 将所有 group的本地逻辑 block ID 放入同一个集合，TP/CP worker 的失败可在 Scheduler 侧 union；不返回 group ID。
SchedulerRecomputeScheduler.update_from_output() 已在 kv_load_failure_policy=fail 时调用 finish_requests(..., FINISHED_ERROR) 并生成 EngineCoreOutput。现有扫描仍按单 group；增加 fail-only 分支，对 tuple[list[int], ...] 展平后做 ID membership 检查。
proxyRequestStatus.FINISHED_ERROR 已映射到错误 finish reason，EngineCore/API 返回链路完整。无需修改 proxy。

关键代码：vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py:584-612、vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_connector.py:589-592、vllm_ascend/core/recompute_scheduler.py:857-865,1058-1076。

二、目标行为与链路

Mooncake transfer/load exception on any group/rank
        │
        ├─ worker records ALL local logical block IDs from every KV group
        ├─ worker exposes get_block_ids_with_load_errors()
        ├─ model runner writes KVConnectorOutput.invalid_block_ids
        ├─ Executor aggregates invalid IDs from all TP/CP workers
        │
        └─ RecomputeScheduler (hybrid + fail policy)
             ├─ obtains all current per-group logical IDs owned by active requests
             ├─ checks shared-BlockPool IDs directly (no group_id needed)
             ├─ any group contains an invalid block → request is affected
             ├─ sync load: evict invalid/dependent cached blocks
             ├─ does not change num_computed_tokens
             ├─ finish_requests(req_id, FINISHED_ERROR)
             └─ EngineCoreOutput(error) → proxy

三、具体修改方案

1. 补齐 MooncakeHybridConnector 的失败采集

文件：vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py

  • 在 KVCacheRecvingThread.__init__() 增加 _invalid_block_ids: set[int] 和锁。
  • 增加私有方法 _mark_failed_recv_request(request_id, local_block_ids)：遍历 local_block_ids 的全部 group，将所有非空 block ID 加入线程安全的 invalid 集合；同一请求的多个 pull task/rank 可重复上报，集合会自动去重。
  • 在 _handle_request() 的统一异常分支调用上述方法，覆盖 _transfer_kv_cache() 和 _transfer_kv_cache_all_groups() 两条路径。
  • 异常后仍执行现有的 _mark_request_task_done()、端口释放和 DONE_RECVING 信号，避免 P 节点资源泄漏；不要因为 fail 改变远端清理协议。
  • 在 MooncakeConnectorWorker 和外层 MooncakeConnector 增加 get_block_ids_with_load_errors()；返回值必须“取出并清空”，与现有 Store/V1 connector 的语义一致。
  • MultiConnector 已经会对各子 connector 的 invalid_block_ids 做 union，因此不需要修改聚合接口；只需确保 Hybrid 子 connector 实现该 getter。
  • 若失败请求已经被 task tracker 标记完成，get_finished() 仍返回该 request；这样 Scheduler 本 step 同时拿到 finished receiving 和 invalid blocks。

2. 修正 MooncakeConnectorV1 的多 group 漏报

文件：vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_connector.py

  • 修改 KVCacheRecvingThread._mark_failed_recv_request()，把当前的 local_block_ids[0] 改为遍历所有 group。
  • 保持 failed_recv_requests、锁和现有 transfer retry/cleanup 逻辑不变；本次只扩大失败 block 的覆盖范围。
  • 如果使用 MooncakeLayerwiseConnector，其 get_finished() 已将失败请求的各 group block flatten 到 invalid 集合，需补一条回归测试确认行为一致。

3. 在 RecomputeScheduler 增加多 group fail 分支

文件：vllm_ascend/core/recompute_scheduler.py

  • 增加通用多 group 判断：仅使用 len(self.kv_cache_config.kv_cache_groups) > 1，不检查 DeepSeekV4 的模型名称或 is_hybrid，避免其他多 group 模型落入父类单 group 解包路径。
  • 增加 _handle_multi_group_invalid_blocks_for_fail(invalid_block_ids)。遍历 self.running 和处于 WAITING_FOR_REMOTE_KVS 的 self.skipped_waiting，取得请求当前持有的全部 per-group block table 并做 membership 检查；connector 上报的是本次真实 load destination，且 active request 在输出处理完成前持续持有 block 引用，因此无需反推不同 spec 的 token→block 映射。任意 group 命中即将 request 加入 affected 集合。
  • 该分支只服务 kv_load_failure_policy=fail：不修改 request.num_computed_tokens，不执行 block 截断，不尝试 recompute。其他策略应在初始化阶段拒绝，而不是静默改变策略。
  • 在 Ascend scheduler 中覆盖 _handle_invalid_blocks()：多 group 且 policy=fail 时调用新分支；单 group 继续调用父类实现，降低回归风险。
  • 保留现有 update_from_output() 的 fail 输出代码（约 1058-1076 行）：调用 finish_requests(..., RequestStatus.FINISHED_ERROR)，为每个 request 生成空 token、错误 finish reason 的 EngineCoreOutput。
  • 同步 load 的失败请求同时收集坏 block 及其后续依赖 block，并在 finish_requests() 前调用 kv_cache_manager.evict_blocks()；异步 WAITING_FOR_REMOTE_KVS 场景保持 evict_blocks=False，避免对尚未写入 prefix hash 的 block 做无意义驱逐。
  • 增加日志：[KVLoadFailure][multi-group] failing requests=%s invalid_blocks=%s groups=%d，同时记录 group 数，便于确认某一 group/某一 rank 的失败已经被汇聚。
  • 核心判定是：any(block_id in invalid_block_ids for group_ids in request_block_ids for block_id in group_ids)。各 group manager 共享一个 BlockPool，scheduler 逻辑 block ID 跨 group 唯一；因此可直接从裸 ID 定位受影响请求，不需要 block_size、compress_ratio 或 page_size_padded 参与反算。命中即返回 request ID，不修改 num_computed_tokens。

4. 配置约束

  • 保留 platform 现有的 is_hybrid + recompute 启动期早拒绝；同时在 RecomputeScheduler.__init__() 的 self.kv_cache_config 已建立后，用 len(kv_cache_groups) > 1 增加通用兜底校验。本需求不放开多 group recompute，也不在 platform 阶段访问尚未生成的 kv_cache_config。
  • 当前分支要使用 RecomputeScheduler 的调度覆盖逻辑，D 节点继续开启 additional_config.recompute_scheduler_enable=True。该开关名称代表使用带 KV 失败处理的 Ascend scheduler，不代表本方案会重算。
  • 若部署不使用 RecomputeScheduler，则必须把同样的 hybrid 分支移植到实际使用的 Scheduler，否则仅修改 connector 不会产生 fail 结果。

四、为什么不返回 group_id

对当前目标而言，失败决策是“请求的任意 group 是否包含失败 block”，不需要知道失败属于哪一个 group。KVCacheManager 的各 group 都从共享 BlockPool 获取 scheduler 逻辑 block ID；Scheduler 遍历 tuple[list[int], ...] 后做集合 membership 检查即可。这样无需同步修改上游 KVConnectorOutput、KVOutputAggregator、model runner 输出和所有 connector 的接口。只有在需要 recompute、按失败 group 截断 token 时，才必须携带 group_id。

扁平 ID 的前提：connector 必须上报 Scheduler 侧的本地逻辑 block ID，而不是经过 TP/CP 展开的 kernel physical ID；失败集合在每个输出周期读取后清空。共享 block 被多个请求复用时，所有引用该 block 的请求一起 fail，这是正确行为。
边界：该方案不承诺多 group 的 recompute。Recompute 需要定义不同 group 的有效前缀、block size、compress ratio 和 token 对齐；本方案明确禁止该路径，只实现 fail。

六、建议实施顺序

  1. 先实现并单测 RecomputeScheduler 的通用多 group fail 分支（包含同步 eviction）；此时 connector 尚未新增上报，空 invalid 集合不会改变现有行为。
  2. 在 RecomputeScheduler.__init__() 中加入多 group + recompute 拒绝校验，并验证单 group/成功路径无回归；不要在 platform 早期阶段访问尚未生成的 kv_cache_config。
  3. 补齐 MooncakeHybridConnector 的 invalid block 采集和外层 getter 接口。
  4. 修正 MooncakeConnectorV1 的 all-group flatten。
  5. 运行完整 UT，再做双节点 P/D 故障注入；确认同一 Executor 内所有 TP/CP worker 的输出被聚合。独立 DP scheduler 不跨 rank 合并，需分别验证请求路由。
  6. 最后接入真实 DeepSeekV4 + Mooncake，观察错误返回、prefix cache eviction 和资源释放。

七、验收标准

  • 任一 KV group、任一同一 Executor 内 TP/CP worker 的 pull/load 失败，最终都能在 Scheduler 侧识别到对应 request；独立 DP scheduler 按各自请求路由独立处理。
  • 请求只执行一次 FINISHED_ERROR，不重复输出 token，不进入 recompute。
  • 失败后 P 节点端口、transfer task 按现有 cleanup 路径释放；同步 load 的坏 prefix block 及依赖 block 从 cache hash 中驱逐，异步 load 不误驱逐未缓存 block。
  • proxy 无需改代码即可收到错误结果。
  • 非 DeepSeekV4、单 group 和成功传输路径行为保持不变。
