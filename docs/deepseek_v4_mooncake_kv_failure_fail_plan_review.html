DeepSeekV4 Mooncake 多 KV Group 失败 Fail 方案 — 可行性评审

评审对象：docs/deepseek_v4_mooncake_kv_failure_fail_plan.html（v2，2026-08-29 更新）　评审日期：2026-08-29（第三轮）　方式：逐项核对方案引用的仓库代码（vllm-ascend 与上游 vLLM），并与 v1 逐行对比。行号随 checkout 漂移，本文件仅对新发现的问题标注行号，已验证事实以"文件 + 函数名"定位。
评审结论（v3）

方案总体可行：对现状的描述准确，核心设计（复用 invalid_block_ids → RecomputeScheduler → FINISHED_ERROR 链路、不引入 group_id、只扫 computed-token 覆盖范围）均与代码事实吻合，实施顺序合理。

与 v2 对比：方案第 3.3 节已修正——明确指出上游不存在 get_block_ids_for_computed_tokens()，需自行实现裁剪逻辑。原评审问题 2（命名错误）已解决。

当前结论：剩余 1 项必改（platform 校验时序，见第三节问题 1）；另有 1 项实施前必须明确——按 group 精确计算有效 block 覆盖范围，禁用任何近似（见第三节问题 3）。在该两项落实前，本评审与原方案均不建议直接作为最终实施依据。

二、设计决策评价

  • 复用 invalid_block_ids 链路、不改上游 dataclass/aggregator：正确。上游 KVConnectorOutput 与 KVOutputAggregator 的 union 语义天然支持扁平集合，改动面最小。
  • 不返回 group_id：论证正确。fail 决策只需"任意 group 是否命中失败 block"的 membership 检查；引入 group_id 需要同步改上游输出结构、聚合器与全部 connector 接口，收益仅对 recompute 有意义，而本方案明确禁止 recompute。
  • 只扫 computed-token 覆盖范围而非全部已分配 block：与上游语义一致，避免 block ID 重用导致的误匹配（被释放又重新分配的旧 ID 恰好落在新请求的 block 列表中）。
  • 保留 P 节点 cleanup 协议：与现状一致——hybrid 的 finally 块中 DONE 信号（mooncake_hybrid_connector.py:601-612）注释明确说明不发会导致远端内存泄漏。
  • 实施顺序（先加 scheduler 空集合分支 → 再接 connector 上报）：回归风险可控，推荐采纳。

三、问题追踪与剩余风险

问题 1（必改，未修正）：多 group 校验存在时序漏洞（会启动报错）

状态：未解决（v2 第 3.4 节未改动）。方案仍建议把 platform.py:_validate_kv_load_failure_policy() 的拒绝条件改为 len(kv_cache_groups) > 1。但该函数在 check_and_update_config 阶段执行（vllm_ascend/platform.py，check_and_update_config 内），而 kv_cache_config 直到 EngineCore._initialize_kv_caches（worker profile 之后）才产生——校验时该配置不存在，直接访问会得到 None/AttributeError。

修正建议（二选一）：

  • 保留现有 is_hybrid 早期校验（hybrid 模型天然多 group），不改动该函数；或
  • 把"多 group + recompute"的拒绝延迟到 RecomputeScheduler.__init__——此处 kv_cache_config 已可用（update_from_output 中已在使用 self.kv_cache_config.kv_cache_groups），可安全访问。

问题 2（v2 已解决）：裁剪逻辑的命名错误

状态：已解决。v1 方案称"优先复用 get_block_ids_for_computed_tokens()"——上游 vLLM 全库不存在此方法；v2 已改为自行实现等价裁剪逻辑，与评审意见一致。

问题 3（实施前必须明确）：按 group 精确计算有效 block 覆盖范围，禁用近似

不能统一套用 block_size × compress_ratio。该公式不适用于当前 Ascend 实现：AscendCompressorStateCache.get_kv_cache_spec()（vllm_ascend/models/deepseek_v4.py，get_kv_cache_spec 方法）构造 AscendSlidingWindowMLASpec 时不传 compress_ratio（dataclass 默认 1），压缩效果已体现在 DSV4 各 group 构造时传入的 group-specific block_size 与 page_size_padded 中（来自 DSV4_BLOCK_SIZES）。各 group（MLA / indexer / compressor-SWA）的 token→block 映射语义不同。

正确要求：按具体 KV group 的 spec/manager 语义精确计算有效 tokens-per-block 与覆盖 block 集合——即在 scheduler 侧按 group 取 kv_cache_spec 的实际 block size（而非 scheduler 统一的 self.block_size，也非任何统一公式）。

禁用近似：向上取整的线性近似是上界而非下界；对非线性布局（如 SWA group）线性近似甚至无良定义的界。高估覆盖范围会把"仅被本请求本地计算引用、不含外部计算 token"的共享 block 误纳入 membership 检查，导致健康请求被误 fail。实现与 UT 都必须按精确映射计算；UT 应覆盖"各 group tokens-per-block 不同"的用例。

四、次要说明（不影响可行性）

  • MooncakeHybridConnector 是 vllm_ascend/distributed/kv_transfer/__init__.py:34 的导出别名，实际类名为 MooncakeConnector（mooncake_hybrid_connector.py:1069），实施时注意定位。
  • Hybrid connector 的 get_finished()（mooncake_hybrid_connector.py:1739）基于 task tracker，失败请求仍会出现在 finished 集合，与方案"Scheduler 同一 step 同时拿到 finished 与 invalid blocks"的预期一致。
  • recompute_scheduler_enable 的 D 节点校验已存在（vllm_ascend/platform.py:677-685），方案第 3.4 节的配置约束描述与现状吻合。

五、最终建议（v3）

两项落实前不建议进入实施：

  1. 必改：修正 _validate_kv_load_failure_policy 的多 group 校验时序——保留 is_hybrid 早期校验，或延迟到 RecomputeScheduler.__init__ 校验；不修正会导致启动阶段 AttributeError/None 访问。
  2. 实施前必须明确：覆盖范围裁剪逻辑按各 group 的 spec/manager 语义精确计算有效 tokens-per-block（不得统一套用 block_size × compress_ratio，不得使用向上取整等近似），并在 UT 中覆盖"各 group tokens-per-block 不同"及"共享 block 位于外部计算范围之外不被误 fail"的用例。

其余部分（connector 失败采集、V1 漏报修正、测试矩阵、实施顺序）可直接按方案执行。
