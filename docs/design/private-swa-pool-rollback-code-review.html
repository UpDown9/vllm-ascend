已修复 · 复核确认A2. Prefill workspace 容量公式漏掉回退 token

原问题：workspace 张量与容量检查按 max_bt + max_num_seqs*(W-1+bs-1) 分配， 漏掉回退项——runner 侧自身 buffer 扩了 W*max_num_seqs 但 workspace 两处公式未同步。 多请求同批命中前缀时 next_page + pages > max_workspace_blocks 必然触发 RuntimeError，且张量本身分配小了，运行时绕不过去（W=128、max_num_seqs=512 时缺口约 6.5 万 token）。

修复结构：

  • 公式集中化：新增 compute_private_swa_prefill_workspace_blocks (private_swa_pool.py:112-135)，运行时分配/容量检查 (dsa_v1.py:1896、1963) 与内存规划预留 (patch_kv_cache_utils.py:355、365) 共用同一函数—— 首轮指出的"两处公式各自维护、易漂移"隐患一并消除。每请求项从 W-1+bs-1 改为 W+bs-1。
  • 正确性（复核逐项验证）：关键不变量为每请求瞬态增量 = max(W-1 history, W rollback)， 不是两者之和： 
    need = Σ ceil((hist_i + rb_i + new_i)/bs)
     ≤ (Σ(hist+rb) + Σnew + S(bs-1)) / bs
     ≤ (S·W + max_bt + S(bs-1)) / bs        ← 每请求 hist+rb ≤ W
capacity = ceil((max_bt + S(W+bs-1))/bs) ≥ need ✓
    不变量成立依赖 A1 修复（rollback 行 history_len=0）：rollback 行 hist=0、rb≤W； 非 rollback 行 rb=0、hist≤W-1——互斥，每请求瞬态 ≤ W。旧代码 rollback 行也带 history（≤W-1）， 瞬态为 2W-1，公式才缺 max_seqs*W。
  • 回归测试已补（tests/ut/core/test_private_swa_pool.py:55-84）： max_bt=2048、S=32、W=128、bs=32，构造 1 个 q=2017 + 31 个 q=1 的全回退批—— 断言 旧公式=222 < 需要=新公式=223，同时证明旧 bug 与新公式的紧确界（构造达到精确等号）。 首轮崩溃构造（32×rb=128+new=2）现在需 64 页 vs 容量 80 页 ✓。

附带观察（耦合告警）：A2 的正确性建立在 A1 的 history_len=0 之上—— 若将来为消灭 B2 剩余的窗口截断近似而恢复 rollback 行的 history，A2 会立即复发且公式无告警。 建议在 compute_private_swa_prefill_workspace_blocks docstring 显式声明 "依赖 rollback 行无 history；若恢复需改为 2W-1 项"（现已写一半）。

已修复 · 复核确认（决策：传输优先）A3. D 节点：传输来的精确私有 KV 被 rollback 重算覆盖

严重 · 数值必错 · 新增发现B1b. FA 压缩注意力范围被 workspace seq_lens 截断

  • FA 调用传 seqused_kv=swa_exec_seq_lens（workspace 局部长度）+ metadata=swa_exec_sas_metadata (dsa_v1.py:2499/2501、2523/2525，后者由 _private_swa_prefill_sas_metadata 以 seqused_kv=workspace_seq_lens 构建)。
  • kernel 侧压缩注意力上界：cmpS2IdLimit = (actOriS2Size - actS1Size + s1EndIdx + 1) / cmpRatio (sparse_attn_sharedkv_swa_kernel.h:380、590)，其中 actOriS2Size 即 seqused_kv：
    • 原路径（全量 seq_lens）：(compute_start + j + 1)/ratio —— 完整因果范围 ✓
    • workspace 路径：(history_len + j + 1)/ratio ≈ (128+j)/ratio —— 仅约 1-2 个压缩组 ✗
  • 后果：任何 confirmed > W-1 的请求（长 prompt 的第 2 块起、所有 rollback 请求）， 压缩注意力被截断到约最后一个窗口；topk（由 lightning_indexer 以全量 seq_lens 计算）选中的更早压缩位置 被 cmpS2IdLimit 过滤丢弃，输出错误。
  • 非本次 B1 修复引入的回归——首轮检视时已存在（当时聚焦写路径漏掉）；影响范围大于 rollback 场景， 覆盖所有私有池开启后的多块 prefill。
  • 修复方向（第七轮复核确认仍未修复：:2077/:2338/:2503/:2527 仍传 workspace 口径）： workspace 的 sas metadata 单独传全量 seq_lens 口径的 cmp 范围 （ori/SWA 部分仍用 workspace 口径），或 kernel 侧改用绝对位置计算 limit。
  • 风险定性（第七轮复核确认）：纯精度损失，无任何功能报错：
    • 不会崩溃/NaN：kernel 侧 actCmpS2Size 只是更小的循环上界—— 少算若干压缩组是合法子集计算，不越界、不触发 assert；即使回退行 j=0、history_len=0 时 limit=0，kernel 的零长检查（仅当 ori 和 cmp 同时为零才跳过）也能安全处理—— ori 部分仍有 [0,j] 窗口，输出 shape 正常；
    • 静默且确定性：被丢弃的 topk 位置（kernel 内被 limit 过滤）不产生错误码或日志， 数值错误但每次相同——回归测试若不比对 logits/ppl 与基线的偏差无法暴露， 必须用长上下文（confirmed > W-1 的多块 prefill）输出对比或 ppl 测试驱动；
    • 影响面：SWA 层的稀疏分支（compress_ratio > 1 的层）对超出 [P-W, P) 之外的历史上下文"失忆"——长上下文场景下表现为召回类质量退化， 而非显式故障。这也是它比 A1-A4 更危险的地方：所有自愈型/报错型防线都探测不到。

已随 A1 修复解决B2. 零历史被计入 softmax

  • 原问题：kernel 侧 oriMaskLeft = max(actS2Size - actS1Size + s1EndIdx - oriWinLeft, 0) (sparse_attn_sharedkv_swa_kernel.h:692-697) 只按窗口宽度截断， 旧实现对回退行 zero-fill 的 workspace 历史槽在 [j-127, j] 窗口内被真实读入并参与 softmax（exp(0)=1 权重），偏差经 KV 传播影响 [H, H+128) 的新 token。
  • 现状：A1 修复中回退行改为 history_len=0 (dsa_v1.py:1953-1956)，零填充方案连同 workspace_flat.zero_() 整体移除——回退行没有历史区域， 窗口掩码只覆盖实际存在的 token（窗口左界被 max(...,0) 截断到 [R, q]）， 即"只 attend 存在的"，与设计文档的 position-based mask 要求一致。
  • 剩余近似语义（设计已知接受）：前 127 个回退 query 的窗口被截断为 [R, q] 而非 [q-127, q]——缺失历史本来就不存在，属确定性近似而非读垃圾。

已随 B1 修复解决B3. mask_shared_slots_for_private_swa_rollback 对最需要保护的组无效

  • 原问题：-1 掩码只作用于各组 slot_mapping (block_table.py:532-556)，而 compressor KV / state_cache / indexer k_cache 的写入槽由 compressor_metadata op 现算，不经过 group slot_mapping——掩码管不到 B1 错位写入的地方。
  • 现状：B1 修复后，compressor/indexer 写路径经由 persistent [H,P) 子批 (dsa_v1.py:2107-2193)，从源头不再触碰 [R,H) 槽位， 本问题被结构性解决。
  • 掩码本身仍保留且仍然必要：full-attention 组的 [R,H) 槽位由它正确置 -1。

行为外溢 · 已给出修复方案B5. notify_kv_cache_written 对所有用户延后

  • dsa_v1.py:2349/2540 把 notify 移到 FA 之后且未按 VLLM_ASCEND_ENABLE_PRIVATE_SWA_POOL 门控——私有池关闭的 DSV4 用户也会丢失 P/D connector 同步事件重叠。
  • 契约：maybe_save_kv_layer_to_connector（dsa_v1.py:1774） 交给 connector 的是注册张量本身。私有池开启时 SWA 注册张量是环，而 prefill 的 scatter 写的是 workspace，环要等 _commit_private_swa_prefill 才有数据——所以事件必须记录在 "最后写环"之后，且越早越好（拷贝流才能与后续计算重叠）。

推荐修复：commit 提前到 FA 之前 + notify 单点放在 FA 之前。 原注释 "Publish the new tail only after FA has consumed the workspace" 过度保守， commit-before-FA 的安全性核查：

检查项结论
commit 读 workspace 尾窗行，FA 也读同一区域read-read，无冲突 ✓
commit 写环，本次 FA 读的是 workspace + compressor cache环对本次 FA 不可见，无冲突 ✓
跨层层间串行，workspace 逐层重建，每层 prepare→scatter→commit→FA 自洽 ✓
多流路径_mla_prolog_multistream 尾部已有 main_stream.wait_stream(aux_stream)，scatter 在 commit 之前有序 ✓
CP 交互私有池 prefill 本就拒绝 PCP/DCP，无交互 ✓

  • compress_ratio > 1 路径同理：SWA scatter（:2320）→ SWA commit → compressor/indexer 计算与 scatter（:2438）→ notify → 两个 FA 调用（:2491/:2516）——注册张量含 compressor cache， notify 放在 compressor scatter 之后、FA 之前。
  • 两种模式都拿回重叠收益（私有池开启时比现状更好——现状拷贝完全串行在 FA 之后）， 且只有一处调用点。
  • 保守备选（不动 commit 位置）：按开关分流——OFF 时 notify 放回原位置 （scatter 后、FA 前），ON 时保持 commit 后。零风险，但两个调用点，私有池用户继续承受串行化。
  • 建议把"定稿 + 通知"封成一个 helper（如 _finalize_swa_prefill_and_notify）， commit 与 notify 永远绑定出现，防止后续改动再次拆开导致错序。
  • decode 路径（dsa_v1.py:2783）不用动：decode 直接 scatter 进环（无 workspace/commit），notify 已在 scatter 后、FA 前，两种模式本来就正确。
